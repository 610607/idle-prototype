# 声明起草

加新系统时，起草它对评估工具的声明：事件归类、指标、成长线、目标、机器人规则、模型系数、文字版。对应 `docs/balance-eval.md`“新系统怎么接入”的清单。产出是草案：人确认后再改 `engine/eval/*.json`、`evalkit/src/bot.rs` 和文字版，`cargo test` 会拦漏掉的部分。

变量：

| 变量 | 内容 | 来源 | 必填 |
|---|---|---|---|
| `{{SYSTEM}}` | 新系统是什么、玩家怎么用、设计意图 | 设计文档或改动说明 | 是 |
| `{{DIFF}}` | 代码改动 | `git diff` 或改动文件列表加关键片段 | 是 |
| `{{EVENTS}}` | 新增或改名的事件 key 及其中文文字 | `locales/zh-CN/events.json` 的改动 | 选填 |
| `{{COMMANDS}}` | 新增的引擎命令 | `engine/src/mech/commands.rs` 的改动 | 选填 |
| `{{CLASSES}}` | 现有事件归类 | `engine/eval/payoff_classes.json` | 是 |
| `{{METRICS}}` | 现有指标注册表 | `engine/eval/metrics.json` | 是 |
| `{{GOALS}}` | 现有设计目标 | `engine/eval/goals.json` | 是 |
| `{{CHECKLIST}}` | 接入清单 | `docs/balance-eval.md`“新系统怎么接入”一节 | 是 |

---

你在帮一个挂机策略游戏原型的评估工具接入一个新系统。评估工具不内置游戏知识，每个系统要自己声明：会产生哪些事件、哪些算玩家能感觉到的爽点、用什么指标量、影响哪些设计目标、机器人怎么用到它。请根据下面的材料起草这些声明。

规则：

- 只根据给你的材料推断。材料里看不出来的，写进“要问的问题”，不要猜一个值填上。
- 爽点级别：0 涓流（不算爽点）、1 小、2 大、3 巨大。拿不准就给 1，并说明理由；挫折和记账类事件记 `"novel": false`。
- 新指标的 id 沿用现有写法（小写、点分、检查点用 `.h{N}`），类别从 `probe`（局面探针）、`result`（结果量）、`model`（模型 ÷ 实测）里选，说明写一句中文。
- 目标优先复用现有的；只有新系统带来了新的体验承诺时才起草新目标，级别先用 `watch`，区间标“草案”并写依据。
- 一切数值都标“草案”，写明依据来自哪里；没有依据的区间不要给。

按下面的格式输出：

````markdown
## 摘要
一两句：这个系统给玩家什么，评估工具要多量什么。

## 1. 事件归类（engine/eval/payoff_classes.json）
```json
{ "event.xxx": { "class": "…", "tier": 1 } }
```
每条一句理由。

## 2. 指标（engine/eval/metrics.json）
```json
{ "pattern": "…", "class": "…", "doc": "…" }
```
每条说明在哪里量（哪个测量钩子、哪个时刻）。

## 3. 成长线
它是否给局内成长；在爽点时间轴上表现为哪类事件；预期幅度怎么算（公式或要量的系数）。

## 4. 设计目标（engine/eval/goals.json）
- 受影响的现有目标：id 和原因
- 新目标草案（如有）：JSON

## 5. 机器人（evalkit/src/bot.rs）
一条让参考机器人用上它的规则（触发条件、做什么），或者为什么需要新人格。

## 6. 模型（docs/balance-model.md）
要量的新系数；模型里缺的机制。

## 7. 文字版
玩家要能看到、做到的新东西，对应 `textui` 的哪部分（局面、菜单、预演）。

## 要问的问题
- …
````
