# 数值评估框架

改一个数，要能回答三个问题：它让哪些指标动了、动了多少、是不是噪声。这份文档定下评估分几层、每层量什么、用哪些机器人、合格区间放在哪、怎么比较两个版本，以及以后加新系统时要补哪几样。工具是 `engine/examples/eval/`，设计目标和合格区间在 `engine/eval/goals.json`。调研和依据见 `reports/数值评估框架设计方法.md`，曲线和单位的定义见 `docs/balance-curves-research.md`。

第一轮读数推翻了一个旧结论：扩张卡在第 3 环，原因不是战斗打不过，而是镇守累积和机器人先清近处的选择。战力指数能把战斗排好序，但刻度偏了好几倍，因为它看不到治疗、护盾、特质和学说。详见“首轮读数”。

## 分层

| 层 | 量什么 | 命令 | 状态 |
|---|---|---|---|
| 数学模型 | 用公式把规则和数据串起来，直接算结果（战斗两道检查、节奏），机器人用来检验它；见 `docs/balance-model.md` | `eval model`、`eval pace` | 战斗、节奏已做，误差 10% 以内；经济、防守、成长未做 |
| L0 静态快照 | 不跑对局，直接从内容数据算曲线：每环遭遇强度 D(r)、相邻环倍数、波数×每波人数、参考小队在各环的 ρ | `eval numbers` | 战斗部分已做；经济价格换算成“产出小时”未做 |
| L1 战斗校准 | 战力指数 ρ 预测真实战斗胜负的能力；各职业、特质、学说实际值多少 | `eval calibrate [lab\|field]` | 已做 |
| L1 词条测价 | 每个特质、装备、学说开 vs 关，值多少环当量；离群的标出来 | `eval price [--bless]` | 已做，`cargo test` 检查有没有漏测价 |
| L2 多种子对局 | 机器人人格各跑 N 个种子，记录按 id 命名的指标，和合格区间比 | `eval run`、`eval check` | 已做，72 小时一局 |
| 爽点时间轴 | 玩家能感觉到的收获的时刻和幅度，间隔、峰值、新奇、战斗墙（见“爽点时间轴”） | `eval run`（自带）、`eval payoff` | 已做；分级阈值待 LLM 试玩校准 |
| L3 多轮回 | 轮回前后的节奏、何时轮回最划算 | — | 未做：没有机器人会轮回 |
| L4 敏感度 | 一次改一个参数（OAT），再到 Morris、Sobol，找出最影响结果的参数 | `eval run --patch '{…}'` | 只有补丁入口；每个变体一个进程 |
| L5 配对比较 | 两个版本按种子配对，给中位差和 90% 置信区间 | `eval compare A B` | 已做 |
| 评估者 | 设计目标逐条判定、自检、覆盖、和基线比，一份报告（见“评估者”） | `eval review` | 已做；目标是草案 |
| 手感 | LLM 或真人按会话协议试玩，事后重放算出同名指标和 `llm.*` 反馈（`docs/eval-interface.md`） | `agent_cli session`、`eval session`、`eval run --sessions` | 已做：重放、过期判定、`llm.*`；只看手感，不作为数值门槛 |

所有输出只有指标 id 和数字，便于 diff，也便于 LLM 读。

```bash
cd engine
cargo run --release --example eval -- run greedy --seeds 20 --hours 72 --out /tmp/a.json
cargo run --release --example eval -- check /tmp/a.json
cargo run --release --example eval -- review /tmp/a.json --out /tmp/report.md
cargo run --release --example eval -- run greedy --seeds 20 --hours 72 --patch '{"warden_route_win": 5}' --out /tmp/b.json
cargo run --release --example eval -- compare /tmp/a.json /tmp/b.json
cargo run --release --example eval -- numbers
cargo run --release --example eval -- calibrate
cargo run --release --example eval -- model
cargo run --release --example eval -- pace --vs /tmp/a.json
cargo run --release --example eval -- price
cargo run --release --example eval -- timeline 0 --hours 48
cargo run --release --example eval -- run greedy --seeds 8 --hours 168 --sessions /tmp/sess   # 每局也写成会话目录 /tmp/sess/greedy-s<种子>/
cargo run --release --example eval -- session /tmp/llm/s0 /tmp/llm/s1 --out /tmp/llm.json     # 重放会话：同名指标 + llm.*
```

在 4 核上：20 个种子 × 24 小时约 9 秒，× 72 小时约 55 秒（越往后机器人每小时要预演的路线越多）；`calibrate` 全套约 10 秒。每个人格都和文字版、试玩会话用同一个开局：第 1 张地图（`ChooseMap 0`），开三条规章（`textui::setup`）。

## 机器人人格

人格是 `examples/bot_policy.rs` 里同一套贪心策略的变体：

- `greedy`：参考机器人，每小时行动一次，先打最近一环。
- `explorer`：先打能赢的最深格子。
- `@N` 后缀：每 N 小时才行动一次（如 `greedy@4`），其余时间交给自动规则。

两个人格之间的差距本身就是一项读数：差距比合格区间还宽，说明这个指标主要由玩家选择决定，数值管不住它。

**盲区规则**：`eval run` 会列出 `commands.never`，即所有人格都没用过的命令。没人用的系统，它的数值就没被量过。当前盲区：`set_squad`、`abandon`、`set_dial`、`dismiss`、`customize`、`retire`、`set_policy`、`set_priority`、`set_gambits`、`equip`、`seal`、`lock`、`reroll`、`archive`、`collapse`。也就是说，装备、街区政策、优先级、定制招募、知识库和轮回都还没有评估覆盖。

以后要加的人格：经济优先（`builder`）、防守优先（`turtle`）、研究优先，以及用来找漏洞的随机合法策略（进化搜索 / MAP-Elites）。

## 指标

L2 指标按 id 记，每个种子一个值；`None` 表示这件事在这局没发生（如没到第 5 环），统计时当作 +∞（删失）。`.hN` 后缀是第 N 小时的检查点（6/12/24/48/72/120）。

| id | 含义 | 备注 |
|---|---|---|
| `owned.hN`、`ring.hN`、`ops.hN`、`score.hN` | 占有格数、最深已占环、队员数、本轮成果 | |
| `reach_h.rK` | 第一次占到第 K 环的时间（小时，5 分钟精度） | 到达时间，删失 |
| `frontier_win.hN`、`deep_win.hN` | 第一支小队按预演能赢的格子比例：下一环（M+1）、再下一环（M+2），走最短路线 | 衡量难度，与机器人选什么无关 |
| `power.hN` | 最强小队的战力指数 S（含学说） | 玩家战力曲线 S(t) |
| `rho_frontier.hN` | 最强小队对下一环各格的 ρ 中位数 | 用前先看 L1 刻度 |
| `route_win.inner/frontier/deep` | 机器人实际路线战斗的胜率 | **有策略偏差**：机器人只打预演会赢的仗，恒为 1；只用来抓预演和实战不一致 |
| `route_battles.frontier` | 在前线打了多少仗 | |
| `surge_lost.all/inside/edge` | 来潮失守率：全部、内部（≤ M−2 环）、边缘 | |
| `share.management/defense/exploration` | 本轮成果的三项占比 | |
| `score_rate.peak_h`、`score_rate.h24_vs_peak` | 每小时成果最高的时刻；第 24 小时的速率占峰值的比例 | 轮回节奏 |
| `stock_h.{scrap,parts,intel}.hN` | 库存折合几小时的收入（用最近 6 小时净增） | 库存水位 |
| `spend_gap.max_h`、`spend_hours.share` | 最长的“无事可花”间隔；有花钱的小时占比 | |
| `research.draws`、`hired` | 研究次数、招募人数 | |

指标按受策略影响的程度分三类，能设的区间也不同：

- **局面探针**：冻结某一时刻问引擎“如果这样会怎样”，不看机器人选了什么，如 `frontier_win`、`deep_win`、`rho_frontier`、L0、L1。可以设绝对区间（局面本身是某个人格走出来的，所以只是弱依赖策略）。
- **结果量**：一局下来发生了什么，由数值和策略共同决定，如 `reach_h`、`owned`、`score`、`share`、`surge_lost`、`stock_h`、`score_rate`。区间要么指定人格，要么按所有人格的范围设。
- **自选样本**：只在机器人自己选的场合才有记录，如 `route_win`。不设区间，只查一致性（预演说赢，实战就必须赢）。

L1 指标（`calibrate` 输出）：

| id | 含义 |
|---|---|
| `calib.auc` | 随机挑一场赢和一场输，赢的那场 ρ 更高的概率：指数排序准不准，和阈值无关 |
| `calib.rho50`、`calib.slope` | 拟合 P(赢) = σ(s·ln ρ + b) 得到的 50% 胜率点和斜率；ρ50 = 1 才说明“ρ = 1 势均力敌”成立 |
| `calib.acc_rho1`、`calib.acc_fit` | 用 ρ > 1 和用拟合阈值预测胜负的准确率 |
| `calib.win_at_rho_ge_1.5`、`calib.win_at_rho_le_0.7` | 旧报告提出的检查：前者应 ≥ 90%，后者应 ≤ 10% |
| `calib.residual.<职业>` | 带这个职业的队伍“实际胜 − 预测胜”的平均值；为正说明指数低估了它 |

战力指数的定义沿用 `docs/balance-curves-research.md` §三：一方 S = √(ΣEHP × Σatk)，EHP = hp × (1 + def / k)，k 取 `combat` 里的减伤常数（伤害 × 1000 / (1000 + def × 22)，k ≈ 45.5）；遭遇 D = √(Σ 各波 S²)，ρ = (S / D)²。技能、标签、治疗、特质都故意不算，L1 的任务就是量出它们值多少。

所有指标 id 登记在 `engine/eval/metrics.json`（模式、类别、一句说明）。`eval run` 产出的 id 和 `goals.json` 里引用的 id 都必须在注册表里，`cargo test` 会拦；`eval metrics [RUN.json]` 打印注册表，带上结果文件时还会列出没登记的 id。

## 爽点时间轴

到达时间只回答“多久进下一环”，回答不了“这一周玩起来爽不爽”。爽点时间轴把一局里玩家能感觉到的每一次收获记成带时刻和幅度的事件，再从整条时间轴算形状指标（`payoff.*`）。依据和取舍见 `docs/payoff-pacing-research.md`。

代码在 `examples/eval/payoff.rs`（事件和指标）和 `examples/eval/strength.rs`（需要战斗模型的幅度）。`eval run` 每 5 分钟把引擎的测量钩子（事件日志条目、战斗、来潮、被接受的命令）交给时间轴，跑完算指标；不需要单独开关。

**事件类别**（`Ev::class`）：

| 类别 | 什么时候 | 幅度 m |
|---|---|---|
| `ring` | 第一次占到第 r 环 | 棋盘面积比：2·log2((2r+1)/(2r−1)) |
| `research` | 选了一个学说 | 参考小队模型强度的 log2 倍数（来自 `strength`）；让前线有格子由输转赢的至少记“小” |
| `contiguous` | 街区连成片 | log2(1.25) |
| `core`、`self_sufficient` | 核心成形；防线第一次自给（每小时查，假变真才算） | 无，记“小” |
| `special`、`drop`、`trait`、`codex`、`rift` | 特殊来客、掉落、特质长成、图鉴点亮、占到裂隙格 | 无，记“小” |
| `frontier_open` 等 | `strength` 给出的其他跳变 | 同 `research` |
| `novelty` | 第一次出现的命令或事件 | 无，记“小” |
| 涓流 | 候选、补给、线索、任务、出征、来潮、招募、反击、规章代做（`auto`）…… | 不算爽点，只在 `eval payoff` 里按小时汇总 |

**分级**：m = log2(之后 ÷ 之前)。“小” ≥ log2 1.2，“大” ≥ 1（翻倍），“巨大” ≥ log2 10。三个阈值都是待校准的常数（`payoff::SMALL/BIG/HUGE`），校准靠 LLM 试玩的 `llm.delight_given_felt` 和 `llm.delight_given_none`（`docs/eval-interface.md`）。

**新奇去重**：命令第一次使用算一次新奇，但第 1 小时用的命令是开局套装，不算（否则 `hook_h` 恒为 0）；事件 key 第一次出现算新奇，除非它本身已经是别的爽点类别、是挫折（失守、团灭、反击失败、放弃、离队）、是轮回记账，或者是同一小时新命令的回声（第一次 `hire` 算，随之而来的第一条“招到了人”不再算）。规章的第一次代做算新奇，之后都是涓流。

**指标**：

| id | 含义 |
|---|---|
| `payoff.hook_h` | 第一个可感爽点的时刻 |
| `payoff.count.<类别>`、`payoff.t.<类别>.<k>` | 各类爽点次数；第 k 次的时刻（研究、连片、自给、核心） |
| `payoff.m.research.<k>`、`payoff.flip.research.<k>` | 第 k 次研究的强度幅度；让几格前线由输转赢 |
| `payoff.gap_max_h.<时段>`、`payoff.gap_p90_h.<时段>` | 相邻可感爽点的最长间隔、90 分位；时段 `d1`、`d2_3`、`d4_7`，间隔按起点归属，时段里没有间隔起点就报覆盖它的那一段 |
| `payoff.gap_max_h.big.<时段>` | 同上，只算“大”以上 |
| `payoff.visit_hit.h<N>` | 每 N 小时回访一次（1/4/8），回访窗口里有可感爽点的比例 |
| `payoff.peak_rank` | 每天最大爽点幅度和天序的秩相关，≥ 0 表示峰值不递减 |
| `payoff.finale` | 最后一天有没有全轮最大或次大的爽点 |
| `payoff.rate_drop.max` | 相邻 6 小时窗口成果增量的最大降幅 |
| `payoff.novelty.d<k>`、`payoff.lines.<时段>` | 第 k 天的新奇数；该时段给出爽点的成长线数 |
| `payoff.auto_share.d<k>`、`payoff.self_sufficient.share` | 规章代做占全部操作的比例；防线自给的小时占比 |
| `payoff.power.h<N>`、`payoff.growth.power`、`payoff.sawtooth.power` | 最强小队对固定标尺（第 1～7 环遭遇）的模型强度；一轮总增长；增长里来自单次可感跳变的比例 |
| `payoff.wall.*` | 战斗墙：前线一格都打不赢的连续小时（次数、最长、占比、墙内无操作的占比、靠研究破墙的比例） |
| `payoff.frontier.margin.h<N>` | 最强小队对前线各格的最佳模型强度 |
| `payoff.model_ratio.research` | 研究时刻：实测 ÷ 模型（`docs/balance-model.md`），中位数 |

**研究和强度怎么量**（`strength.rs`）：

- 模型强度 S：最强小队对固定标尺（第 1～7 环各 8 场，共 56 场遭遇）的战斗模型余量的几何平均，`payoff.power.h*`。战斗模型只看攻击、生命、防御和职业系数，看不到只加效果的学说（反应、转化、回复）。
- 模拟胜场 L：最强小队在完整标尺上用战斗模拟能赢的场数。标尺是第 1～7 环各 8 场，再加第 7 环的 6 档加强（×1.25～×3.0），共 104 场（`payoff.ladder.size`；读数等于它就是顶到天花板，`eval review` 会提示）。L 能看到效果类学说。L 只在第 1 小时、各检查点、最后一小时和每次研究时读，每个种子 168 小时约多花 1 秒。
- 每次研究记 S 的 log2 倍数（`payoff.m.research.<k>`）、前线由输转赢的格数（`payoff.flip.research.<k>`）和 L(之后) − L(之前)（`payoff.ladder_gain.research.<k>`，可为负）。三者任一为正，研究事件至少记“小”；时间轴备注写成 `research.new bloodhound flips=0 ladder=+26`。
- 战斗墙：前线一格都打不赢的连续小时（`payoff.wall.*`）；前线余量 `payoff.frontier.margin.h*`。

单局逐条看：

```bash
cargo run --release --example eval -- payoff 0 --hours 168          # 可感爽点一行一条，涓流按小时汇总，最后是本局的 payoff.* 指标
cargo run --release --example eval -- payoff 0 greedy@4 --patch '{…}'
```

**首次读数**（`greedy`，8 个种子 × 168 小时，p50）：

- 第 9 小时以后没有“大”爽点：只有进第 1、2 环够“大”，`gap_max_h.big` 三个时段都是 159 小时。
- 峰值逐天下降：`peak_rank` −0.63，`finale` 0。
- 新东西几乎都在第一天：`novelty.d1` 9.5，第 2 天 2，第 3 天起 0。
- 最长间隔：第一天 7.2 小时，第 2～3 天 10.9，第 4～7 天 18.5；每 4 小时回访一次，只有 62% 的回访有东西可看。
- 研究：第 1～6 次在第 2、4.5、30、55、62、66 小时，之后 8 个种子里只有 3 个做到第 7 次。
- 规章代做的比例从第一天 11% 升到第七天 36%。
- 强度：模型强度 S 一轮只涨 log2 0.25（约 ×1.19）；模拟胜场 L 第 6～24 小时 52 场，第 48 小时 56.5，第 72 小时起停在 81 左右（满分 104），之后四天不再增长。一轮研究合计多赢 28.5 场，几乎都来自 `bloodhound`（第 46～66 小时，每次 +20～+33）；`react` 每次 +3～+7；`spall` 每次 −2～−5。模型幅度 m 和前线翻绿格数全是 0。
- 战斗墙：一周里没有出现（`payoff.wall.count` 0）。前线余量第 6 小时 7.75，第 72 小时 2.65，第 168 小时 1.79，始终远大于 1。

## 设计目标和合格区间

合格区间挂在设计目标下面，放在 `engine/eval/goals.json`（原来的 `bands.json` 已并进去）。每条目标用一句话写体验，绑定几项指标的区间：

```json
{
  "id": "week_cycle", "kind": "experience", "level": "gate",
  "text": "一轮约一周：参考玩家进第 r 环的时间接近 τ_r = 4r(r−1)+1 小时（±20%）",
  "doc": "docs/balance-eval.md 已定",
  "checks": { "reach_h.r3": [{ "stat": "p50", "min": 20, "max": 30, "missing_fails": true, "personas": ["greedy"] }] }
}
```

- `kind`：`experience` 是游戏该有的样子；`selfcheck` 是评估工具自己还可信（模型和实测一致、爽点分级贴近玩家感觉、试玩接口好用）。
- `level`：`gate` 的检查不过，`check` 和 `review` 以退出码 1 结束；`watch` 只报告。单条检查也可以写 `"watch": true`。
- `stat` 取 `p10`、`p50`、`p90`（跨种子）。
- `personas` 为空表示对所有人格都适用；以 `*` 结尾表示前缀，如 `llm:*` 是所有 LLM 试玩。
- `missing_fails`：缺值当 +∞ 算并判失败，适合到达时间这类指标。不设时，统计量落在缺值上就显示 `n/a`，不判失败（比如地图边缘外没有“下一环”）。
- 目标里的指标 id 必须在注册表里，`cargo test` 会拦。指标改名或退役时，目标显示“无法判断”，不会悄悄通过。
- **读法**：同一条区间，所有人格都不过，问题在数值；只有部分人格不过，问题在策略，或者区间设在了不该设的指标上（思路同 Riot 的“任一玩家群体超上限就算过强，所有群体都低于下限才算过弱”）。

当前的目标和区间全部是**草案**，要逐条确认：

- 到达时间改成一周目标 τ_r ±20%（1、9、25、49、81、121、169 小时）；第 7 环只观察，因为一周的运行刚好到不了 169 小时。原来按 72 小时一轮定的 2/5/10/18/30/48/72 小时已作废。
- 原有区间都保留：来潮失守率 0.10～0.25、内部失守 ≤ 0.05，第 72 小时废料库存 2～10 小时收入，三项成果占比各 0.20～0.45，最长无事可花 ≤ 4 小时，第 24 小时下一环可赢 0.3～0.8、再下一环 ≤ 0.3。成果速率峰值（48～96 小时、第 24 小时 ≤ 峰值的 70%）是按 72 小时一轮定的，改为只观察，等重定。
- 新加的都只观察：战斗墙和前线余量、局内成长（一周研究约 9 次）、开局钩子、回访命中率、峰值不递减和高潮、新东西不断档、LLM 试玩的惊喜率，以及三条自检。依据见各目标的 `doc`。

## 评估者

单项工具回答“这个数是多少”，评估者回答“游戏现在怎样、评估本身还可不可信”。它分三层，游戏知识不写死在评估代码里：

1. **声明**：每个系统自己告诉评估者它有什么，每样都由 `cargo test` 强制。事件归类在 `eval/payoff_classes.json`，指标登记在 `eval/metrics.json`，词条价格在 `eval/prices.json`，命令要进文字版菜单（`textui::reach`），机器人没用过的命令进 `commands.never`。游戏一变，测试先失败，声明跟着改，评估不会悄悄失效。
2. **测量**：谁来玩都产出同一种会话目录，`eval session` 用同一套重放算全部指标（`docs/eval-interface.md`）。机器人给稳定的参考线；LLM 和真人试玩覆盖机器人还不会用的新东西。
3. **评判**：`eval review` 拿运行结果对照设计目标，出一份报告。

```bash
cargo run --release --example eval -- run greedy --seeds 8 --hours 168 --out /tmp/greedy.json
cargo run --release --example eval -- review /tmp/greedy.json [/tmp/llm.json …] --out /tmp/report.md
cargo run --release --example eval -- review /tmp/greedy.json --bless     # 有意改数值以后，更新基线
```

报告分四节：

- **一、设计目标**：每条目标过、不过、未达（观察）或无法判断，每项检查附基线值和按种子配对的变化（90% 区间）。
- **二、自检**：自检目标，加上自动发现：注册表里类别为 `model` 的比值偏离 1 超过两成，模拟标尺封顶，会话过期，指标没登记，和基线相比消失或新增的指标。游戏一改，最先出问题的应该是这一节。
- **三、覆盖**：没人用过的命令，目标引用了但运行里没有的指标，没有适用运行的目标，没有目标约束的指标。
- **四、和基线比**：显著变化的指标，按相对变化排序，标出相关目标。

基线在 `engine/eval/baseline/<人格>.json`，是提交进仓库的一份运行结果（`greedy` 8 个种子 × 168 小时）。`review` 默认和它比；种子数或时长不同就标“不可比”。运行结果记录游戏版本（`build`，即 `content::fingerprint`），报告里并排显示。

数字判断全部由代码确定性地完成。需要大模型的事只用提示词模板（`docs/prompts/`）：试玩玩家、读报告的分析员、新系统进来时起草声明。模型的产出都是草案，人确认后才进仓库。

## 统计方法

- **种子数**：每次提交 20 个，每晚 100 个。所有统计都看分位数（p10/p50/p90），不看平均值，因为删失值和长尾会把平均值拖偏。
- **删失**：没发生的事件记 +∞ 参与排序；达成率 `reached/n` 和分位数一起输出。以后到达时间可以换成 Kaplan–Meier 生存曲线。
- **配对比较**：A、B 用同一组种子，逐种子算差值，再用 2000 次自助抽样给中位差的 90% 置信区间；区间不含 0 就标 `*`。有一侧缺值的种子不进差值，但两侧各有几个种子有值会单独列出，所以“原来到不了、现在到了”这种变化不会被藏掉。引擎所有随机都走同一条 `state.rng` 流，一个改动可能让后面的随机全部错位，配对的效果因此打折扣。以后可以按子系统拆分随机流（地图、招募、来潮、掉落各一条），并量一下配对后方差降了多少。
- **多重比较**：`compare` 一次比八十多个指标，按 90% 置信度，纯噪声也会冒出 8 个左右的 `*`。门槛只设在 `goals.json` 里少数几个关键指标上；其余 `*` 只当线索，复跑或加种子确认。以后可以按 fishtest 的做法：先小样本，结果不明再加样本（序贯检验）。
- **可复现**：同样的输入跑两次，输出文件逐字节相同（已验证，多线程也一样）。这是比较的前提，以后放进测试。

### 从读数看到的

1. **扩张的瓶颈不在战斗。** 第 6 小时的小队已经能拿下第 4 环全部、第 7 环三分之二的格子；`explorer` 20 小时就占到第 7 环。`greedy` 到 41 小时才进第 3 环，是因为格子要攒满镇守才能占：开局第 1 环 90、第 2 环 40、第 3 环起是 0，每次路线胜利 +10，也就是第 1 环赢 1 场、第 2 环 6 场、第 3 环起 10 场；巡逻只慢慢加，来潮失守还会扣（`start_warden_by_ring`、`warden_route_win`、`warden_patrol`、`warden_surge_loss`）；而它又总是先清近处。旧报告把“停在第 3 环”归因于第 3→4 环强度翻倍，这个解释不成立。
2. **战力指数排序准，刻度偏。** AUC 0.93～0.97，说明谁强谁弱判断得对；但胜率 50% 的点在 ρ ≈ 0.4（实验室）到 0.1（实战），不是 1。最大漏项是续航：拆开看一场第 7 环胜仗，先锋替队友挡下全部伤害，医疗兵一场回了 1650 点血，敌人的输出被回复抵消，打成了消耗战，第 35 回合取胜。特质和学说在高环各值 20～30 个百分点的胜率。
3. **战力几乎不成长。** 最强小队的 S 从第 6 小时到第 24 小时不变（149），第 48 小时也只到 164（+10%）。战斗上的成长感目前来自研究学说，而且来得很晚。
4. **节奏整体偏快、偏满。** 成果速率第 6～8 小时就到峰值（提议 48～96 小时）；废料积压 40～70 小时的收入（提议 2～10 小时），说明花钱的地方不够或太便宜；来潮失守率 0.22～0.63。
5. **研究的价值被策略遮住了。** `docs/llm-playtest.md` 里脚本玩家研究与不研究的成果只差 1%～2%，看上去研究没用；但上面的对照里，学说把第 7 环胜率从 0.36 提到 0.65。只是贪心机器人从不去需要它的地方。内容的价值要用开关对照量，不能只看某个人格的结果。
6. **人格差距大于区间宽度。** 同一版数值，到达第 3 环的时间从 5 小时到 41 小时不等。到达时间这类区间必须先指定“参考玩家”是哪个人格，否则无法判定。

## 词条测价

每个战斗词条（特质、装备、学说）都按“开 vs 关”测价，单位是环当量：固定 5 支基准小队（参考小队排第一）打一遍遭遇阶梯，小队得分是能打下的环数期望（各环胜率之和）。特质和装备每次只给一名队员，三个位置轮一遍，`mean` 是平均值，`best` 是放在最合适位置时的值；学说给全队，和对局里一样。

- 结果存在 `engine/eval/prices.json`。`cargo test`（`tests/eval_prices.rs`）会检查内容里的每个词条都有价格，没有就失败：新词条必须先跑 `eval price --bless`，记下的价格和变化随改动一起提交、一起审。
- `eval price` 不加 `--bless` 时，会打印每条和已记录价格的差值，用来看一次数值改动让哪些词条涨跌了。
- 同类里偏离中位数超过 3 个绝对中位差的标 `OUTLIER`；全零的标“无战斗效果”，这类词条（过天险、雾中行走等地图效果）要用 L2 指标或专门的对照来评。
- 首次读数：学说里 `overclock`（+0.30 环）和 `react`（+0.23 环）偏高；`ionize` 单独测为 0，它要和 `react` 配合才生效，组合要成对测（未做）。

## 新系统怎么接入

加一个系统或词条时，同一个改动里补齐：

0. **词条**：新特质、装备、学说跑 `eval price --bless`，看它落在同类的什么位置；`cargo test` 会拦漏测价的。
1. **数值进数据**：常数放 `balance.json` 或内容数据（`CLAUDE.md` 已有规定）。
2. **L0**：如果它有随环、随时间变化的曲线，在 `numbers` 里加一行，打印曲线和相邻倍数。
3. **L2 指标**：在 `examples/eval/run.rs` 里加 id。按事件计的结果走 `GameState::trace` 钩子（不存档，`None` 时没有开销），不要靠轮询状态去猜。
4. **有人用**：给 `bot_policy.rs` 加一条会用它的规则，或者加一个人格；否则它会出现在 `commands.never`，等于没被评估。
5. **目标和区间**：在 `goals.json` 里把它挂到相关的设计目标下（或起草新目标），区间写明依据（来自哪条曲线或哪个参考游戏），没把握的先用 `watch`。可以用 `docs/prompts/declare.md` 起草。
6. **战斗相关的**：在 `calibrate` 里加一个开关对照（像 `no_doctrines`），用“开 vs 关”的胜率差给它定价；如果它改变了 AUC 或 ρ50，说明指数需要加项。
7. **模型**：新职业、新敌人跑 `eval model` 量出系数；改了战斗或节奏规则，先用 `eval pace --patch` 算预期，再用机器人验证，模型和实测差超过两成就要补模型。
8. **玩家看得到的**：按 `CLAUDE.md` 同步文字版。
9. **爽点声明**：新的事件 key 在 `engine/eval/payoff_classes.json` 里归类（爽点类别和级别，或明确记为不算），`cargo test` 会拦没归类的；新的成长线要能在时间轴上出现（`payoff.lines.*`）。
10. **指标登记**：新指标 id 写进 `engine/eval/metrics.json`。

## 已定

- **参考玩家是 `greedy`**。到达时间等节奏区间只按 `greedy` 判（`goals.json` 里 `reach_h.*` 带 `"personas": ["greedy"]`），其他人格只看相对 `greedy` 的差距。
- **扩张门槛由战斗强度卡**，不再由镇守累积卡。怎么落地见 `docs/balance-model.md`“反推”，要先定下面第 1 条。
- **新系统、新词条都复用这套评估**：按上一节的清单接入，词条测价由测试强制。
- **一轮按一周排**：参考玩家进第 r 环的目标时间 τ_r ≈ 4r(r−1)+1 小时（节奏模型的吞吐量下限）。
- **组织等级是周回成长**：组织经验只在收束防线时结算，局内不升级；一周之内它是常数，决定这一轮的起点。局内成长靠研究学说。
- **节奏模型要算爽点，不只算战斗**：自动化、新系统、过门槛的大幅提升都要进模型和指标，怎么量还在调研。

## 待讨论

1. **局内成长的量**：战斗要当门槛，参考小队的输出在一轮里就得涨上几倍（现在 48 小时只涨 10%），这部分要由研究学说（以及设施、装备是否算进来）提供，组织等级只抬起点。
2. **爽点怎么进模型**：哪些事件算爽点、间隔和幅度的合格区间、规章要不要改成解锁。
3. **战力指数**：已由“两道检查”的战斗模型取代（刻度误差三成以内）；ρ 只保留做对照。
4. **区间数值**：上面的提议区间要不要逐条确认或改。
5. **提交门槛**：哪几个指标失败要拦提交，其余只报告。
6. **随机流拆分**：要不要为了配对比较把 `state.rng` 按子系统拆开（会改变所有种子的结果，要把 `SAVE_VERSION` 加一）。
