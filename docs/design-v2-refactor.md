# 设计 v2：引擎重构的计划和规格

2026-11-28，已确认，进行中（进度见文末）。对应 [计划](design-v2-plan.md) 的阶段 2：把现有的游戏搬到 [引擎模型](design-v2-engine-model.md) 的类型上，**玩法一点不变**。本文写三件事：现在的代码长什么样、要改成什么样、分几步改以及每步怎么验。

文里的行号是 2026-11-28 主干上的，动手前以代码为准。类型草图是方向，名字和字段在实现时可以调，约束（哪些东西必须只有一份、顺序必须固定）不能调。

## 一句话

- 分 4 段 15 步：先搭安全网，再搬实体，再搬容器，最后搬效果和战斗。
- 每一步结束都能编译、能玩、所有对照物逐字节相等，然后才提交。
- 对照物有三样：战斗报告、整局的局面轨迹、六个参考玩家的读数。前两样是这次新加的，因为现在没有任何逐字节的检查。
- 不在这次做的：血量保留、医疗、品质和合并、守备阵型、挪建筑、秒级节奏、解锁登记表。重构只把地基换掉，这些在后面的阶段加。

## 现在的代码和目标差在哪

| 方面 | 现在 | 目标 |
|---|---|---|
| 实体 | 队员、小队、格子、街区各有各的结构；建筑、装备、学说没有状态，只是一个字符串 id | 都是实体：编号、定义、品质、标签、状态、所在位置 |
| 关系 | 手工存两份：小队记成员、队员也记所属小队；街区记格子、格子也记街区 | 只存一份：实体记自己在哪个容器的哪个位置，成员列表是查出来的 |
| 前后排 | 由职业决定，不是位置 | 是小队容器里的位置；默认位置由职业给，结果和现在一样 |
| 建筑 | 格子的一个字段（`TileUse`） | 放在格子槽里的实体 |
| 归属 | 格子上的 `owned` 字段 | 阵营容器 |
| 战斗单位的身份 | 字符串：`"op:12"`、`"fac:clinic"`、`"militia"`、`"hq_guard"`、`"doctrine:react"`，靠前缀判断种类 | 实体编号；来源是定义 id |
| 守城建筑 | 单独一条造单位的路（`fixture_unit`）加一个 `fixture` 开关 | 声明“可出战”的建筑，出战方式写在数据里 |
| 属性 | 六七处各算各的：`operative::derived`、`doctrine::apply`、`armory::apply`、`simple_unit`、`fixture_unit`、`enemy_spec` | 一条属性管线，修正的来源和顺序固定 |
| 效果 | 四套枚举：技能效果 8 种、词条效果 21 种、反应效果 4 种、战术规则（条件 11 种、目标 8 种、触发 5 种），外加设施、政策、敌人各自的结构 | 一种句式：时机、条件、对象、结果、代价 |
| 标签 | 写死的 6 个，`[i32; 6]` 散在各处；侵蚀掉血、坚固每次挨打掉一层等写在战斗代码里 | 数据里定义，数量不写死；每个标签的数值行为写在标签定义里 |
| 战斗 | 2700 行一个文件，调度和效果混在一起 | 调度是专用代码；回合里发生的事都走句式 |
| 按名字认内容 | `data/hooks.rs` 里 12 个常量 | 能用标签或接口表达的去掉，剩下的才留 |

有一处要更正：之前的文档写过“模拟每 5 分钟一步”，这不对。模拟是按事件跳的（`kernel/clock.rs` 的 `Timeline`），没有固定步长。教学关要按秒走，真正的限制是几个常数：一趟出征最短 60 秒，经济每小时结算一次，来潮每 4 小时一次。这属于阶段 3，不在重构里；相关文档的说法已经改掉。

## 原则

1. **玩法不变。** 任何一步如果让对照物变了，要么是改错了，要么是原来的行为里有没看懂的地方。先查清，不“顺手修”。原来的行为即使看着像 bug 也照搬（下面“必须照搬的行为”一节列了已知的）。
2. **一步只搬一样东西。** 每步结束提交并推送，对照物全绿。不攒大改动。
3. **先换数据的形状，再换代码的路。** 比如效果：先让旧的内容文件在读入时翻译成句式、战斗照旧结算，对上了，再改内容文件、删翻译层。
4. **对外的样子不变。** 命令的格式、网页拿到的局面数据、文字版的输出、会话记录，重构期间都不变。内部怎么存随便改。
5. **存档不迁移。** 每一步只要存档结构变了，`SAVE_VERSION` 加一。
6. **不为将来的功能多写代码**，但类型上留位置：品质字段现在全是最低档；“取下建筑”引擎支持、玩家用不到。

## 对照物

### 现有的检查不够

- 战斗没有任何逐字节的检查，只有 7 个性质测试。
- 会话重放检查的是存档的摘要（`save_sha`），存档结构一变就失效，正好在这次重构里用不上。
- 读数基线（`engine/eval/baseline-pre-refactor/`）是统计量，能发现大偏差，发现不了小的。

### 新加三样

| 对照物 | 内容 | 存在哪 | 怎么跑 |
|---|---|---|---|
| 战斗报告 | 一组固定的战斗输入，每场存带记录的完整报告的摘要 | `engine/tests/golden/battles.json` | `cargo test`，每次都跑 |
| 局面轨迹 | 六个参考玩家各 1 个种子、24 小时。每个游戏小时存：局面数据（网页拿到的那份）的摘要、这一小时新事件文字的摘要 | `engine/eval/golden/trace-<玩家>.json` | `eval golden`；`cargo test` 里跑一条短的（贪心、6 小时） |
| 读数 | 现有的 `baseline-pre-refactor`，六个玩家各 3 个种子、72 小时 | 已有 | `eval run` 加 `eval compare --exact`：每个指标、每个命令次数都相等才算过 |

- 战斗输入的范围：每种敌人在第 1、3、5 环各一场；每个职业的起始队员；每条学说单独带一场；每种带守城效果的设施一场来潮；民兵 1 到 3 队；一场核心；一场会全灭的；一场会紧急撤退的；一场计划撤退的。输入由现有的 `route_battle`、`surge_setup` 在固定种子上产生。
- 局面数据的摘要取自 `client/view.rs` 的输出，不取存档，所以存档结构怎么变都不影响。
- 会话重放：`final.json` 加一个可选字段 `view_sha`（只加可选字段，协议版本不用动，在 `docs/eval-interface.md` 写明）。重构期间用它验证；每次 `SAVE_VERSION` 加一后，确认 `view_sha` 相等，再把 `save_sha` 重新记一遍。
- 文字快照：`text_snapshot` 在第一步前跑一遍存下，每步之后比对。
- 速度：第一步前记下 `eval run greedy --seeds 3 --hours 72` 的用时。每步之后不超过它的 1.5 倍；超了先查原因再往下走。

### 每一步的检查单

```
cargo fmt && cargo test                      （含战斗对照、短轨迹、分层、文字棘轮）
cargo run --release --example eval -- golden （六条轨迹）
文字快照比对
```

每一段（A、B、C、D）结束再加：

```
六个参考玩家的 eval run + eval compare --exact
会话重放（view_sha）
用时
npm run wasm、npx tsc --noEmit -p .（在 web/）
文字版跑一遍 new 和 do
```

## 目标类型

放在哪一层：

| 东西 | 层 | 说明 |
|---|---|---|
| 实体表、编号、位置、容器的通用操作 | 引擎 `kernel` | 不知道游戏内容，只管“谁在哪” |
| 实体定义、接口的数据块、句式、标签定义 | 数据 `data` | 从内容文件读 |
| 属性管线、句式的执行、战斗调度、摆放规则 | 机制 `mech` | |

### 实体

```rust
// kernel
pub struct EntityId(pub u32);

pub struct Entity<S> {
    pub id: EntityId,
    pub def: DefId,          // 定义 id，指向内容数据
    pub tier: u8,            // 品质；重构期间全是 0
    pub tags: Tags,          // 留着不清的标签（现在都是空的，战斗里的标签不出战斗）
    pub at: Option<Place>,   // 在哪个容器的哪个位置；None 表示不在任何地方
    pub state: S,            // 状态，由机制层定义
}

pub struct Place { pub container: ContainerId, pub slot: Option<Slot> }
```

状态按接口分块，不按种类分：

```rust
// mech
pub struct State {
    pub persona: Option<Persona>,   // 名字、出身、九项属性、特质、经历计数、战术规则、锁定
    pub fighter: Option<Fighter>,   // 休整到几点；将来放血量
    pub ground: Option<Ground>,     // 格子：地形、镇守度、是否露出、原住民、波次、危险度、裂隙等
    pub squad: Option<SquadState>,  // 路线、在途的一趟、上一趟
    pub district: Option<DistrictState>,
}
```

- 一个实体有哪些块，由它的定义声明了哪些接口决定。代码问“有没有这个块”，不问“是不是队员”。
- 编号：现有队员的编号不能变（它出现在局面数据和战斗报告里）。队员沿用现在的计数器；新成为实体的东西（格子、建筑、装备和学说的实例、小队、街区）从一个高位段发号。格子的编号等于高位段加格子下标，这样按格子下标遍历的顺序不变。
- 候选人现在整个队员结构嵌在候选列表里，改成“在候选容器里的实体”。

### 定义和接口

现在的职业、敌人、设施、装备、学说、政策各有各的定义结构。统一成：

```rust
// data
pub struct EntityDef {
    pub id: DefId,
    pub tags: Vec<TagId>,           // 类别标签：队员、民兵、敌人、医疗、防御……
    pub placeable: Option<Placeable>,   // 可放置：能放在什么槽里
    pub fighter: Option<FighterDef>,    // 可出战：基础数值、技能、默认指令、出战方式
    pub mover: Option<Mover>,           // 可行进
    pub passable: Option<Passable>,     // 可经过
    pub fitting: Option<Fitting>,       // 可装配：装到什么宿主的什么槽
    pub converter: Option<Converter>,   // 可转化：经济上的投入产出（保持现有字段）
    pub slots: Vec<SlotDef>,            // 有槽位
    pub scoring: Option<Scoring>,       // 计分
    pub effects: Vec<Sentence>,         // 这个实体带的效果
}
```

- 内容文件还是分开放（`classes.json`、`facilities.json`……），读进来以后进同一张定义表。
- 可出战的“出战方式”有两种：**上场**（占位置、能被选中、有回合）和**支援**（不占位置、不能被选中、没有回合、只用被动技能）。现在的守城建筑就是支援。这是数据里的一个字段，取代代码里的 `fixture` 开关。
- 民兵和总部守卫现在是代码里拼出来的，改成内容数据里的两个定义，技能和默认指令写在数据里。
- 敌人的指令现在是代码按技能生成的（带“消耗某标签”的技能配“敌人有这个标签”的条件）。这条生成规则保留成一个函数，定义里写“指令：自动”的就用它。

### 容器

```rust
// kernel
pub struct Container {
    pub id: ContainerId,
    pub owner: Option<EntityId>,    // 挂在哪个实体上（小队的队列、队员的装备槽、格子的槽）
    pub shape: Shape,               // 有位置：行列或槽名；没有位置
}
```

重构后有这些容器：

| 容器 | 有没有位置 | 成员 | 取代现在的 |
|---|---|---|---|
| 棋盘 | 有（15×15） | 格子 | 格子数组的下标 |
| 格子的建筑槽 | 有（1 个槽） | 建筑 | `TileUse` |
| 格子的驻守槽 | 有（1 个槽） | 队员 | `Assignment::Garrison` |
| 小队的队列 | 有（前排、后排，各有序号） | 队员 | `Squad.members` 和 `Assignment::Squad` |
| 队员的装备槽 | 有（1 个槽） | 装备 | `Operative.equipment` |
| 学说槽 | 有 | 学说 | `Cycle.doctrines` |
| 替补席 | 没有 | 队员 | `Assignment::Idle` |
| 候选 | 没有 | 队员 | `Cycle.candidates` |
| 库存 | 没有 | 装备、（将来）建筑 | `Cycle.inventory` |
| 街区 | 没有 | 格子 | `District.tiles` 和 `Tile.district` |
| 阵营 | 没有 | 格子 | `Tile.owned` |

通用操作只有三个，所有“装上去、派出去、造出来”都走它们：

- `fits(实体, 位置)`：这个实体能不能放进这个位置，按接口和槽的要求判断。
- `place(实体, 位置)`：放进去；原来在别处就先取出。
- `swap(甲, 乙)`：两边互相 `fits` 才换。

几点说明：

- **一个实体同时在几个容器里**，设计上还没定。重构里的做法：`at` 只记一个“所在位置”（棋盘、槽、队列这类）；街区和阵营这两种按规则或划定的归属，单独各存一份成员表。以后定了再统一。
- **学说现在是全局的**，对出征和守城的全体己方生效。设计上学说是装在小队上的，但那是玩法改动。重构里学说槽先挂在阵营上，行为和现在一样；挪到小队是阶段 4 的事。
- **住宅**现在是格子用途的一种，没有设施定义。改成一个建筑定义，id 登记到 `hooks.rs`。
- 命令的格式不变。`Build`、`Equip`、`SetSquad`、`Garrison` 内部都变成 `place`。

### 属性管线

一个入口：给一个实体和它所处的场合，返回属性表。

```rust
pub fn attrs(world: &World, id: EntityId, scene: &Scene) -> Attrs
```

修正按固定的顺序收集，顺序就是现在各处代码实际的顺序：

1. 定义的基础值（职业、敌人、设施）。
2. 自己的状态推出来的（队员九项属性的换算公式）。
3. 自己带的效果（特质，然后经历特质）。
4. 自己槽里的东西（装备）。
5. 场合给的（设施给守军的效果；敌人按环数和危险度的缩放）。
6. 宿主容器上的（学说）。
7. 阵营上的（军械，按类别标签区分给队员还是给民兵）。

- 属性分两类：数值（生命、攻击、防御、速度、行动点、被动点、九项属性）和规则开关（一次行动能触发几个被动、标签碰到一起会不会反应、标签溢出去哪）。规则开关是“这一侧只要有一个在场的成员带着就算有”，和现在一样。
- 地图层的几个标记（揭示加成、穿越屏障、雾中行走、共享驻守）也是属性，由地图代码来读。
- 属性不存档。每次要用就算；慢的话在局面修订号不变时缓存。
- 截断顺序会影响结果（全是整数的万分比乘法，每步向下取整），所以上面的顺序是规格的一部分，不能为了好看调换。

### 标签

```rust
// data
pub struct TagDef {
    pub id: TagId, pub max: i32,
    pub dealt_bp: i32, pub taken_bp: i32, pub taken_mode: AddOrMul,   // 带着它打人、挨打的修正
    pub dot_bp: i32, pub dot_decay: i32,                              // 每回合掉血、每回合掉几层
    pub lose_on_hit: i32,                                             // 每次挨打掉几层，算作“被消耗”
    pub backed_by: Option<Gauge>,                                     // 护盾：层数跟着护盾值走
}
```

- 标签的个数由 `tags.json` 决定，代码里不再有 `[i32; 6]`，改成按标签下标的小数组。标签的先后顺序就是文件里的顺序（共鸣、增幅、释放蓄积都按这个顺序）。
- 现在写在战斗代码里的四条标签行为搬进定义：侵蚀每回合掉血并掉一层；坚固每次挨打掉一层并算被消耗；过载同时加打人和挨打；护盾的层数由护盾值决定。
- 护盾值是可出战状态里的一个量，不是标签层数。这一条例外保留并写明。
- 城市那边的标签（医疗、防御、居住……）和战斗标签进同一张表。城市标签现在只做类别用，没有层数行为。

### 效果句式

```rust
// data
pub struct Sentence {
    pub when: When,            // 时机
    pub conds: Vec<Cond>,      // 条件（全部满足）
    pub who: Who,              // 对象
    pub then: Vec<Outcome>,    // 结果，按顺序
    pub cost: Cost,            // 代价
}
```

**时机**

| 时机 | 取代现在的 |
|---|---|
| 常驻 | 没有触发时机的词条：属性加成、伤害加成、规则开关、地图标记 |
| 入场时 | 开场标签 |
| 回合开始 | 再生；侵蚀掉血 |
| 被指令选中 | 主动技能 |
| 己方被瞄准、己方挨打、己方血量低于某线 | 被动技能的三种触发（血量线现在写死 45%，改成参数，值不变） |
| 标签落下、标签被消耗、标签跳动 | 被动技能的两种触发；转化词条的三种事件 |
| 自己命中 | 命中附加标签 |
| 护盾破裂 | 护盾爆裂 |
| 每隔多久 | 现有内容不用；探针用 |

**条件**：现有 11 种战术条件原样保留，加上“在守城中”“对象带某标签”“自己带某标签”。

**对象**分两层，这是现有数据本来的样子，照搬：

- 主对象，由指令或触发事件给出：默认、前排血最少、先打后排、攻击最高、带某标签的、标签最多的、血最少的队友、自己。
- 每个结果可以再指一个相对的对象：主对象、自己、攻击者、对方全体、对方其余、本方全体。

**结果**

| 结果 | 取代现在的 |
|---|---|
| 伤害（倍率、按哪项属性、消耗哪个标签、对带标签的加成） | 技能的伤害 |
| 加标签、扩散、增幅 | 同名技能效果；反应的加标签和扩散 |
| 治疗、给护盾、自伤 | 同名技能效果；再生；消耗回血 |
| 按最大生命的比例直接扣血 | 反应的爆发；消耗爆裂；护盾爆裂 |
| 代为承受 | 掩护 |
| 加行动点、加被动点 | 共鸣；反应的额外行动；标记回被动点 |
| 标签转成别的标签 | 转化 |
| 改属性 | 常驻的数值加成 |
| 开规则开关 | 连锁、溢出、标签反应、吸收 |
| 伤害修正（阶段、万分比） | 低血加伤、对带标签的加伤、以自身标签加伤 |
| 离场 | 计划撤退、紧急撤退 |
| 交换位置 | 现有内容不用；探针用 |

**代价**：行动点、被动点、每回合次数（共鸣和额外行动现在共用一个“每回合一次”，写成同一个计数器）。

**指令**（战术规则）用同一套条件和对象：`如果 条件，用 哪个技能，打 谁`，或者 `如果 条件，离场`。

**反应表**（`reactions.json`）每一行也是句式：时机是“标签落下”，条件是“对象同时带着另一个标签”，结果里先消耗两个标签。

句式之外保留的专用数据：设施的投入产出和相邻加成、政策的经济字段、军械的轨道、任务、成长规则。它们属于“城市产出的公式保持专用代码”，这次不动。设施和政策里和战斗有关的部分（给守军的标签和效果、来潮强度）改成句式。

### 战斗

战斗 = 两个有位置的容器进了战场，加一份场合信息。

```rust
pub struct Battle<'a> {
    pub ours: ContainerId,          // 小队的队列，或守城时临时组的防守队列
    pub theirs: Vec<Vec<EntityId>>, // 一波一波的敌人（临时实体）
    pub scene: Scene,               // 是不是守城、环数、危险度、场地给两边的标签、接地
}
```

专用代码只留调度，拆成一个单独的文件：

- 波次循环、回合循环、每回合重置行动点和被动点、15 回合上限。
- 出手顺序。
- 按指令选技能和主对象。
- 被动的排队：谁先响应、一次行动每人几次、连锁深度上限 4、扣被动点。
- 触发事件的发出点和先后：每个新落下的标签一次“标签落下”，然后“己方挨打”，然后“标签被消耗”，然后“血量低于线”。
- 死亡判定的时点、撤退、胜负、组装报告和日志。

其余全部是句式的执行，放在另一个文件里，城市那边将来也用它。

伤害的计算拆成固定的几个阶段，每个伤害修正声明自己在哪个阶段。阶段和顺序照现在的代码：

1. 属性加成：`倍率 × (10000 + max(0, 属性 − 40) × 50) / 10000`。
2. 攻击方自己的标签（过载）。
3. 攻击方带的效果，按挂上去的顺序。
4. 技能对带标签目标的加成。
5. 消耗标签的加成。
6. 乘攻击力，过防御：`原始 × 1000 / (1000 + 防御 × 22)`。
7. 防御方标签里按加法算的（震荡、过载），加在一起。
8. 防御方标签里按乘法算的（坚固）。
9. 下限 1。
10. 在下限之后加的固定值（消耗爆裂）。

写死在代码里的几个数（45%、每人每回合最多 6 次行动、连锁深度 4、防御系数 22、属性的 40 和 50）搬进 `balance.json`，值不变。

出征的战斗现在在出发时就算好、到点才生效，这个做法不动。阶段 3 血量要留到下一场时再改。

### 必须照搬的行为

下面这些看着像可以“顺手理顺”，但一动结果就变。重构里原样保留，各配一条测试；想改的话在重构之后当成数值改动来做。

1. 死亡是延后的：血量到 0 以后，在这次行动结算完之前仍然算活着，后面的伤害、标签、反应照样落在它身上。
2. 伤害各阶段每步向下取整，阶段顺序见上。
3. 坚固挨打掉的那一层算“被消耗”：进报告、能触发“消耗时”的效果，但不算进消耗爆裂。
4. 一个触发事件只让一个被动响应：按前排优先、序号、编号的顺序，第一个够条件的单位的第一个够条件的技能。支援单位也在这个队里。
5. 一次行动之后的固定顺序：记消耗 → 消耗引起的转化 → 落下引起的转化 → 标签反应 → 反应引起的消耗和转化 → 判死 → 共鸣 → 发触发事件。被动引起的结算走同样的顺序，但目标是己方时跳过，没造成伤害时不发触发事件。
6. 共鸣和反应的额外行动共用每回合一次。
7. 记账上的几处不对称：收到的标签在被吸收之前就记数；打在护盾上的伤害全额记给攻击方；护盾爆裂的反伤不过攻击方的护盾；给护盾记作治疗，波间回血不记给任何人。
8. 日志编号在不记录日志的那次计算里也照常递增；行动和被动的日志条目先占位、后填内容，快照是行动之前的。
9. 来自同一个来源的全侧规则只算一次（学说对全队只生效一次），单位自己带的效果每个单位各算各的；溢出规则由被加标签一方的对面持有。
10. 学说和军械不给支援单位；敌人不带词条；开场标签里“只在守城时”的那些、接地、波间回血只在守城时有。
11. 敌人的数值：生命和攻击按环数和危险度缩放，防御加 `(环数 − 1) / 2`，速度和点数不缩放，九项属性全是 50。

## 出了问题怎么办

- **对照物不相等。** 先用战斗对照定位到哪一场、哪一条日志开始不同（报告里有完整日志）。查不出就回退这一步，拆得更小再来。
- **某条现有内容写不成句式。** 先加一种结果或时机。如果加到十种以上还不够，说明五段句式不够用，停下来回到引擎模型重谈。
- **D4 怎么也对不上。** 退一步：战斗内部先不搬，句式只做到翻译层（D3）和内容文件（D6 反过来，由句式翻译回旧结构来结算）。其余照做，后面的阶段不受影响，只是城市那边暂时用不上同一套执行代码。
- **变慢超过 1.5 倍。** 先看属性管线有没有重复算，加缓存。实体表的查找换成按下标的数组。
